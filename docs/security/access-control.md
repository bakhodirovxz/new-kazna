# Разграничение доступа

## 1. Модель

Пользователь → должность → роль → разрешения + область данных. Роль назначается должности, а не
человеку (ТЗ, раздел 9). Проверка выполняется только на сервере: каждый маршрут API объявляет
требуемое разрешение (`require_perm`), маршруты без явного разрешения требуют действующей сессии;
фронтенд лишь скрывает недоступные элементы. Отказ из-за отсутствия разрешения записывается в
журнал аудита (`security.access_denied`). Тесты: `test_every_non_public_route_requires_session`,
`test_admin_and_audit_routes_require_matching_permission`, `test_all_protected_routes_return_401_without_session`.

Правила пароля (`backend/app/auth/passwords.py`): длина не менее 12 символов, не менее трёх классов
символов из четырёх, пароль не содержит логин и слова из списка контекстных и распространённых
паролей, не повторяет ни один из последних 5 паролей.

Вход требует пароля и второго фактора (TOTP) для всех ролей. Временный пароль, выданный
администратором, пользователь обязан сменить при первом входе; пароль действует 90 дней (остаточный риск R8 в [threat-model.md](threat-model.md)).
Сессия завершается через 30 минут бездействия и не позднее чем через 12 часов после входа.

## 2. Матрица ролей

Роли создаются при первом запуске (`backend/app/auth/permissions.py`), далее управляются
администратором.

|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| Руководство | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | — | — | все филиалы |
| Начальник отдела финансирования и контроля денежных потоков | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | — | — | все филиалы |
| Специалист казначейства | ✓ | ✓ | ✓ | ✓ | — | — | — | — | — | ✓ | — | — | все филиалы |
| Экономист филиала | ✓ | ✓ | — | — | — | ✓ | ✓ | — | ✓ | ✓ | — | — | филиалы должности |
| Профильная служба (шаблон) | ✓ | — | — | — | — | — | — | — | — | ✓ | — | — | все филиалы |
| Администратор | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | все | ✓ | все филиалы |
| Служба внутреннего контроля | ✓ | — | — | — | — | — | — | — | — | — | — | ✓ | все филиалы |

Соответствие ТЗ (раздел 1): «Профильные службы — свой раздел и Обзор». Перечень служб в ТЗ не
задан, поэтому системная роль «Профильная служба» — шаблон (Обзор + выгрузки), а роль конкретной
службы (например, «Служба закупок»: Обзор + Закупки + выгрузки) администратор создаёт в интерфейсе
и назначает должностям — [../ops/admin-guide.md](../ops/admin-guide.md), раздел 4.

Разрешения разделов и выгрузок управляют меню и доступом к данным; страницы данных разделов и
выгрузки таблиц появляются в следующих этапах (сейчас реализованы вход, администрирование, журнал
аудита, ключи, состояние загрузок и справочные данные).

## 3. Разрешения

| Разрешение | Что даёт |
|---|---|
| `section:<раздел>:view` | просмотр раздела и его данных (9 разделов) |
| `export:csv`, `export:xlsx` | выгрузка таблиц |
| `admin:users` | пользователи: создание, изменение, блокировка, сброс пароля и 2FA |
| `admin:roles` | роли и должности, привязка филиалов |
| `admin:settings` | пороги «Требует внимания», допущения финмодели, настройки витрины, загрузок, качества данных и оповещений; OpenAPI в prod |
| `admin:security` | политика входа и сеансов, ограничения частоты запросов, срок хранения журнала аудита, пороги контроля эксплуатации; изменение — с причиной и кодом 2FA |
| `admin:integrations` | параметры и учётные данные внешних систем (SMTP и др.), проверка подключения; изменение — с причиной и кодом 2FA |
| `admin:etl` | журнал загрузок, ручной запуск, сборки витрины и откат |
| `admin:keys` | состояние ключей шифрования, ротация DEK |
| `audit:read` | просмотр, выгрузка и проверка журнала аудита |

Новое разрешение, добавленное в код, один раз выдаётся существующей роли «Администратор»
(`test_new_permission_is_granted_to_admin_role_once`). Ключ каждой настройки проверяется на сервере:
`admin:settings` не даёт менять настройки безопасности (`test_settings_admin_cannot_change_security_key`).

Гарантии: у роли «Администратор» всегда есть `admin:users` и `admin:roles`; последнего активного
администратора нельзя заблокировать или лишить прав (`test_last_admin_is_protected`), пользователь
не может заблокировать себя (`test_cannot_block_self`). Изменение должности, роли, пароля или 2FA,
блокировка завершают все сеансы пользователя (`test_block_revokes_sessions`,
`test_change_position_revokes_sessions`).

## 4. Область данных (RLS, два уровня)

1. **API.** Область вычисляется из должности (все филиалы или список). Запрос вне области → 403 и
   событие `security.rls_violation_attempt`.
2. **СУБД.** В начале каждой транзакции задаются `app.branch_ids` и `app.scope_all`; на таблицах
   `dwh`, `mart` со столбцом `branch_id` включены `ENABLE` и `FORCE ROW LEVEL SECURITY`;
   представления `pub` работают с `security_invoker`. Без заданного контекста видно 0 строк; итоговая
   строка «все филиалы» (`branch_id = 0`) — только для области «все».

Проверки: `test_rls_scopes`, `test_branch_rls_for_app_role`, `test_pub_views_and_mart_rls_direct_sql`
(прямой SQL от `ugk_app`), `test_branch_economist_sees_only_own_branch_even_after_cache_warmup`
(API с прогретым кэшем), `frontend/e2e/specs/branch-scope.spec.ts` (браузер) — критерий приёмки 2 ТЗ.

## 5. Роли СУБД

| Роль | Назначение | Права |
|---|---|---|
| `postgres` | инициализация кластера, резервное копирование | только локальный сокет (peer); по сети запрещён |
| `ugk_migrator` | миграции, операции с ключами (rewrap, retire), перешифрование `dwh.*` при ротации | владелец схем; используется только оператором |
| `ugk_app` | API | `pub` — чтение с RLS; прямое чтение `mart.agg_*`, `dwh.dim_branch`, `dwh.dim_item`; `core` — ограниченно (учётные записи, сессии, настройки, очередь загрузок; смена активной сборки — `UPDATE(status, published_at)` в `core.builds` и `UPDATE(active_build_id, published_at)` в `core.data_version`); аудит — чтение и функции записи; ключи — `SELECT, INSERT, UPDATE(status, retired_at)`; прямого доступа к фактам и зашифрованным реквизитам нет; `NOBYPASSRLS` |
| `ugk_etl` | загрузки ETL | запись в `stg`, `dwh`, `mart`, журналы загрузок; `core.data_version`; чтение `core.crypto_keys` (для шифрования реквизитов при загрузке); `NOBYPASSRLS`; нет доступа к таблицам аудита |

Тесты: `test_app_role_cannot_create_tables`, `test_app_role_has_no_bypassrls`,
`test_app_role_cannot_read_facts`, `test_etl_role_cannot_select_audit_log`, `test_app_role_cannot_delete_users`.

## 6. Инфраструктура

| Субъект | Доступ |
|---|---|
| Администраторы ОС (группа `ugk-admins`) — требование к серверу | SSH по ключу из VPN, `sudo` с журналированием auditd; членство в группе `docker` эквивалентно root — только эта группа ([../ops/host-hardening.md](../ops/host-hardening.md)) |
| Хранители ключей (2 сотрудника) | сейф с копиями KEK и секретов — только вдвоём (организационная мера, [key-management.md](key-management.md)) |
| Контейнеры | не от root (db и backup — UID 70, redis — 999, остальные — 10001); каждому выдаются только нужные секреты (например, `caddy` — только TLS; `backup` — только пароль репозитория) |

## 7. Периодический пересмотр

Ежеквартально владелец системы и служба внутреннего контроля сверяют список пользователей,
должностей и ролей с кадровым составом; результат — запись в журнале аудита (изменения) и акт
сверки. Учётные записи уволенных сотрудников блокируются в день увольнения. Это организационная
мера: система её не выполняет и не контролирует автоматически.
