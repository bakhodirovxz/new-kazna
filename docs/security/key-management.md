# Регламент управления ключами и секретами

Регламент основан на жизненном цикле ключей NIST SP 800-57 (создание, хранение, использование,
ротация, вывод из обращения, уничтожение). Все команды выполняются на сервере в каталоге текущего
релиза (`/opt/ugekazna/current`) пользователем из группы администраторов, переменная:

```bash
P="docker compose -f deploy/compose.prod.yml --env-file deploy/prod.env --env-file deploy/release.env"
```

Для основных операций есть эквивалентные цели Makefile. Параметр `STACK=prod` задаётся только в
командной строке (`make rotate-keys PURPOSE=pii STACK=prod`; значение из переменной окружения
игнорируется). На сервере, где в каталоге `deploy` есть файл `prod.env`, команды стенда разработки без
`STACK=prod` отклоняются.

## 1. Реестр секретов

Файлы секретов: владелец `root`, группа контейнеров (10001 или со сдвигом userns-remap, если он
включён на хосте), права `0440`, каталог `0750` — `scripts/secrets_perms.sh`. Секретов нет в коде,
образах, переменных окружения и репозитории (gitleaks в CI и pre-commit).

## 2. Роли

Роли хранителей ключей — организационные меры: их назначает и контролирует организация, система
не обеспечивает схему «двух хранителей» технически.

- **Администратор ОС** (служба ИТ) — выполняет процедуры, не имеет права единолично извлекать копию
  KEK из сейфа.
- **Хранители ключей** — два сотрудника (служба ИБ и служба ИТ), вскрытие сейфа — только вдвоём,
  с записью в журнале сейфа.
- **Администратор приложения** — ротация DEK из интерфейса («Ключи шифрования», разрешение
  `admin:keys`); интерфейс перешифровывает только столбцы схемы `core` (см. П3).

## 3. Процедуры

### П1. Первичное создание

```bash
python3 scripts/gen_secrets.py /opt/ugekazna/shared/secrets
cp <сертификат>.pem /opt/ugekazna/shared/secrets/tls_cert.pem
cp <ключ>.pem /opt/ugekazna/shared/secrets/tls_key.pem
sudo scripts/secrets_perms.sh /opt/ugekazna/shared/secrets
```

Скрипт не перезаписывает существующие файлы и отказывается работать через символические ссылки.

### П2. Резервная копия KEK и других невосстановимых секретов

Без `master_kek` зашифрованные поля и проверка журнала аудита невосстановимы, без
`pgbackrest_cipher_pass` — резервные копии. Сразу после П1 и после каждой смены:

1. Создать архив `tar -C /opt/ugekazna/shared -cf - secrets | gpg --symmetric --cipher-algo AES256 > ugk-secrets-<дата>.tar.gpg`
   (пароль архива знают только хранители ключей, каждый — половину).
2. Записать архив на два съёмных носителя, вычислить `sha256sum`, носители опечатать и поместить в
   сейф; в журнал сейфа внести дату, контрольную сумму и идентификатор KEK (поле `fingerprint`
   события `admin.key.rewrapped` или вывод `sha256("ugk-kek-id|"+ключ)[:16]`). Идентификатор
   файла KEK (32 байта в base64) вычисляется так:
   `{ printf 'ugk-kek-id|'; base64 -d < master_kek; } | sha256sum | cut -c1-16`.
3. **Хранить все прежние KEK**, пока существуют резервные копии, в которых DEK обёрнуты ими
   (срок хранения копий — 14 полных копий, см. [../ops/backup-restore.md](../ops/backup-restore.md)),
   плюс срок хранения архивных копий, если они выносятся за пределы репозитория.

### П3. Ротация DEK (плановая — раз в 12 месяцев, внеплановая — при подозрении на утечку)

Рекомендуемый способ — командная строка, она перешифровывает все зарегистрированные столбцы:

```bash
make rotate-keys PURPOSE=pii STACK=prod
# или: $P run --rm -T migrate python -m app.cli rotate-key --purpose pii
```

Назначения: `pii`, `bank`, `mfa`, `integration_creds`, `audit_meta`, `audit_chain`.
Создаётся новая активная версия, прежняя переходит в `decrypt_only`. Перешифровка выполняется в
две транзакции: сначала версия и столбцы схемы `core` (`core.users.totp_secret_enc`,
`core.sessions.ip_enc`; роль `ugk_app`), затем столбцы схемы `dwh` (`inn_enc`, `account_enc`; роль
`ugk_migrator`). Если вторая транзакция не завершилась, старая версия остаётся в использовании и
вывести её нельзя (П4); команду следует повторить. Если выполняется загрузка ETL, команда
отказывается работать (код возврата 3) — повторить позже. Событие `admin.key.rotated`
(`result = "fail"` при ошибке).

Из интерфейса: «Администрирование → Ключи шифрования → Ротировать» (`admin:keys`). Интерфейс
создаёт версию и перешифровывает только столбцы схемы `core`; реквизиты витрины (`pii`, `bank`)
остаются на старой версии, пока оператор не выполнит команду выше. Для `audit_meta`, `audit_chain`
и `integration_creds` перешифровывать нечего: создаётся новая версия, старые записи журнала остаются
зашифрованными прежними версиями, которые не выводятся.

### П4. Вывод старых версий из обращения (crypto-shredding)

Не ранее чем через 10 минут после П3 (кэш ключей 60 с):

```bash
make retire-keys STACK=prod
# или: $P run --rm -T migrate python -m app.cli retire-keys --grace-minutes 10
```

Выполняется от роли `ugk_migrator` (у приложения нет права изменять `wrapped_key`). Цель
`make retire-keys` не принимает параметров и использует минимальный интервал 10 минут; больший
интервал задаётся только прямой командой. Выводятся версии `decrypt_only`, которые не используются ни
одним зарегистрированным столбцом, для назначений `pii`, `bank`, `mfa`; активная версия должна быть
старше интервала. Обёрнутый ключ стирается, статус `retired`; событие `admin.key.retired` по каждому
назначению. Назначения `audit_meta` и `audit_chain` не выводятся никогда, `integration_creds` — пока
его столбцы не зарегистрированы. Копии старых DEK остаются в резервных копиях до истечения их срока
(риск R12 в [threat-model.md](threat-model.md)).

### П5. Смена KEK (rewrap) — плановая раз в 24 месяца, в окно обслуживания

Процессы `api` и `worker` держат ключи в кэше и при перечитывании используют KEK, с которым были
запущены: после перешифрования они перестали бы расшифровывать DEK. Поэтому смена выполняется с
остановкой:

1. Внеочередная полная копия: `$P exec -T backup ugk-backup once full` (или `make backup TYPE=full`).
2. Новый KEK: `umask 077; head -c 32 /dev/urandom | base64 > /root/ugk-new-kek`, затем
   `chgrp <группа секретов> /root/ugk-new-kek && chmod 0440 /root/ugk-new-kek`.
3. Остановка: `$P stop caddy api worker`.
4. Перешифрование DEK (одна транзакция, роль `ugk_migrator`; после успешной фиксации — событие
   `admin.key.rewrapped` с полем `fingerprint` нового KEK):
   ```bash
   $P run --rm -T -v /root/ugk-new-kek:/run/new_kek:ro migrate \
     python -m app.cli rewrap-keys --new-kek-file /run/new_kek
   ```
   (или `make rewrap-keys f=/root/ugk-new-kek STACK=prod`; путь абсолютный)
5. Замена секрета: прежний файл сохранить для сейфа, новый — на его место:
   `install -m 0440 -o root -g <группа> /root/ugk-new-kek /opt/ugekazna/shared/secrets/master_kek`.
6. Запуск и проверка: `$P up -d`, вход в систему, `make audit-verify STACK=prod`.
7. П2 для нового KEK; прежний KEK — в сейф (хранится по правилу П2.3); `shred -u /root/ugk-new-kek`.

Команда отказывает, если новый KEK не 32 байта или совпадает с текущим. Откат: если шаг 4
завершился ошибкой — изменений нет (одна транзакция; в журнал пишется `admin.key.rewrapped` с
`result = "fail"`), запустить сервисы со старым KEK. Если после шага 5 сервисы не стартуют
(`unwrap_failed`) — проверить, что файл `master_kek` содержит новый ключ; старый KEK после успешного
шага 4 уже не подходит.

### П6. Смена паролей ролей СУБД

```bash
$P exec db psql -U postgres -d ugekazna
ugekazna=# \password ugk_app
```
`\password` вычисляет SCRAM-верификатор на стороне клиента — пароль не попадает в журнал СУБД
(при `log_statement = 'ddl'` команда `ALTER ROLE … PASSWORD '…'` записала бы его открыто).
Затем записать новый пароль в файл секрета и перезапустить потребителей:
`$P up -d --force-recreate api worker` (для `ugk_migrator` — только файл; для `ugk_etl` — `worker`).

### П7. Смена пароля Redis

Записать новое значение в `redis_password`, затем `$P up -d --force-recreate redis api worker`.

### П8. Замена сертификата TLS

Файлы `tls_cert.pem` (полная цепочка) и `tls_key.pem` заменить, выполнить
`$P up -d --force-recreate caddy worker`. Срок действия контролирует ops-check (`tls_cert_expiring`,
предупреждение за 30 дней, критично за 7).

### П9. Компрометация `session_pepper`

Новое значение → `$P up -d --force-recreate api worker`. Все сессии, CSRF-токены, открытые challenge
и резервные коды 2FA становятся недействительными: пользователи входят заново (секреты TOTP не
затронуты, они зашифрованы DEK `mfa`); администратор выполняет сброс 2FA («Сбросить 2FA») для
выпуска новых резервных кодов — [../ops/admin-guide.md](../ops/admin-guide.md).

### П10. Компрометация `blind_index_key`

Новое значение → перезапуск `api worker`. Blind index используется при загрузке для обнаружения
изменений (поиск по индексу пока не реализован), поэтому функции системы не нарушаются: очередные
загрузки справочников пересчитывают индексы, строки с изменившимся индексом перезаписываются.
Для немедленного пересчёта выполнить загрузки всех источников справочников. Полная загрузка
файлового источника требует явного флага `--allow-full-replace` (каждый CSV должен содержать все
строки за всю историю); `make etl-run` этот флаг не передаёт — режим `full` для файлов выполняется
прямой командой `$P exec -T worker python -m app.cli etl-run --source file --mode full --allow-full-replace`.

### П11. Пароль репозитория копий

Для существующего репозитория pgBackRest пароль изменить нельзя. При компрометации: создать новый
том и новый пароль, `stanza-create`, выполнить полную копию; старый репозиторий хранить до
появления 14 полных копий в новом (или уничтожить сразу, если компрометирован и носитель).

### П12. Компрометация KEK

1. Немедленно П5 с новым KEK.
2. П3 для **всех** назначений: `pii`, `bank`, `mfa`, `audit_meta`, `audit_chain`,
   `integration_creds` (последнему пока нечего перешифровывать). Злоумышленник, получивший KEK и
   обёрнутые ключи (дамп БД, резервная копия), знает все действующие DEK; без ротации записи аудита
   будущего подписывались бы (`audit_chain`) и шифровались (`audit_meta`) известными ему ключами.
   Новые версии защищают записи, создаваемые с этого момента.
3. П4 (вывод старых версий) — только для `pii`, `bank`, `mfa`: их данные уже перешифрованы ключами,
   которых злоумышленник не видел. Старые версии `audit_meta` и `audit_chain` не выводятся и не
   перешифровываются: они нужны для расшифровки IP/UA и проверки старых записей. Проверка
   цепочки берёт ключ по `chain_key_version` каждой записи, поэтому цепочка, охватывающая несколько
   версий `audit_chain`, проверяется целиком. Записи аудита, созданные до смены, считать не
   защищёнными от подделки со стороны этого злоумышленника, а IP/UA в них — раскрытыми.
   До и после смены выполнить `make audit-verify STACK=prod`; значение `core.audit_head.last_hash`
   занести в журнал сейфа.
4. Считать скомпрометированными все резервные копии, созданные до п. 1 — ограничить доступ к
   носителям, по истечении срока уничтожить.
5. Реагирование по [incident-response.md](incident-response.md) (сценарий СЦ4).

## 4. Контроль

- Все операции с ключами фиксируются в журнале аудита: `admin.key.rotated`, `admin.key.retired`,
  `admin.key.rewrapped`; сбои при ротации, выводе и смене KEK записываются с `result = "fail"`
  (без ключевого материала); действия на хосте — auditd.
- Возраст активных DEK (более 365 дней — `key_rotation_due`) и срок сертификата проверяет ops-check
  каждые 15 минут ([../ops/monitoring.md](../ops/monitoring.md)). Возраст KEK автоматически не
  контролируется — по журналу сейфа.
- Организационная мера: раз в год — сверка журнала сейфа с реестром секретов и тестовое восстановление с ключами из сейфа.
