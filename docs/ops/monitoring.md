# Мониторинг и оповещения

## 1. Автоматический контроль

`scripts/ops/monitor.sh` запускается таймером `ugekazna-monitor.timer` каждые 15 минут и:

1. проверяет, что сервисы `db`, `redis`, `api`, `worker`, `caddy`, `backup` запущены и не в
   состоянии `unhealthy`;
2. выполняет `ops-check` внутри `worker` с отправкой письма ответственному (`SMTP_HOST`, `SMTP_TO` в
   `prod.env`) при любых замечаниях; без SMTP замечания видны только в журнале запуска (`journalctl -t ugekazna-monitor`).

Письмо отправляет только `worker`. Если он не запущен, `monitor.sh` пишет в syslog запись уровня crit
(тег `ugekazna-monitor`); при любом замечании скрипт завершается с кодом 1, юнит systemd считается
неуспешным и `ugekazna-alert@` пишет crit с тегом `ugekazna-alert`. **Пересылка этих записей в SIEM
обязательна** ([host-hardening.md](host-hardening.md), раздел 9): иначе при отказе почтового пути
оповещения никто не увидит.

Журнал: `journalctl -t ugekazna-monitor -t ugekazna-alert`; вручную — `make monitor`.

Ожидаемый шум оповещений: скрипт завершается с кодом 1 при любом замечании, включая предупреждения, и
каждые 15 минут пишет crit `ugekazna-alert`, пока замечание не устранено. Сразу после установки так
будет до первой проверки восстановления (`restore_test_missing`), а `stale_data` будет повторяться,
пока администратор не запустит загрузку (автоматического расписания на prod нет). Настройте в SIEM
свёртку повторов.
Таймеры используют `Asia/Tashkent` (systemd ≥ 235).

## 2. Проверки состояния контейнеров

| Сервис | Healthcheck | Смысл |
|---|---|---|
| `api` | `GET /api/v1/healthz` (живость процесса) | процесс отвечает |
| `worker` | метка времени `/tmp/worker-heartbeat` не старше 3 минут | планировщик работает |
| `db` | `pg_isready` через сокет | СУБД принимает подключения |
| `redis` | `redis-cli ping` | Redis отвечает |
| `caddy` | `http://127.0.0.1:8081/health` внутри контейнера | Caddy работает |
| `backup` | `ugk-backup health` | последняя копия успешна и не старше 7 часов |

## 3. Готовность (`/api/v1/readyz`) и деградация

`/api/v1/readyz` возвращает 200, если доступны СУБД и Redis, и 503, если нет; тело ответа —
`{"status": "ok|fail", "checks": {"db": true|false, "redis": true|false}}`.
Снаружи путь закрыт (404), проверяется изнутри:
```bash
$P exec -T api python -c "import urllib.request as u; print(u.urlopen('http://127.0.0.1:8000/api/v1/readyz', timeout=3).read().decode())"
```
**Недоступность Redis — деградация, а не отказ**: API продолжает работать без кэша, лимиты запросов
временно отключаются (fail-open), блокировка входа после 5 ошибок продолжает действовать (хранится в
СУБД). Поэтому healthcheck контейнера `api` использует `healthz`, а не `readyz` — Docker не
перезапускает API из-за Redis. Ответ 503 от `readyz` — сигнал «Предупреждение»: восстановить Redis
(`$P up -d redis`).

## 4. Коды ops-check

| Код | Уровень | Значение | Действие |
|---|---|---|---|
| `host` | критично | сервис не запущен или `unhealthy` (передаётся из monitor.sh) | `$P ps`, `$P logs <сервис>`, `$P up -d` |
| `ops_check_error` | критично | проверку не удалось выполнить (например, СУБД недоступна); текст ошибки очищен | `$P ps`, `$P logs db` |
| `clock_skew` | критично | часы приложения и СУБД расходятся более чем на 60 с | `chronyc tracking`; при расхождении более 5 минут запись аудита отклоняется |
| `audit_partition_missing` | критично | нет партиции журнала аудита на следующий месяц | проверить задачу `partitions` в журнале worker |
| `wal_archiver_failed` | критично | последняя попытка архивации WAL завершилась ошибкой | `$P logs db`, `$P logs backup`; доступность репозитория копий |
| `wal_archiver_lag` | критично | есть неархивированные завершённые сегменты WAL, последняя архивация старше 20 минут | то же |
| `archive_timeout_invalid` | предупреждение | `archive_timeout` вне диапазона 1 с — 15 мин | проверить `deploy/postgres/postgresql.conf` |
| `audit_default_rows` | предупреждение | записи аудита в партиции по умолчанию | то же; записи переносятся при создании партиции |
| `stale_data` | предупреждение | данные не обновлялись дольше порога `freshness.max_age_hours` (по умолчанию 6 часов, ТЗ раздел 9) | «Состояние обменов», журнал worker |
| `etl_request_stuck` | предупреждение | запрос загрузки в очереди дольше 30 минут (или в работе дольше 6 часов) | журнал worker (`$P logs worker`), перезапуск worker |
| `load_users_present` | критично | в БД prod остались нагрузочные учётные записи `load_*` с известным паролем | удалить вручную от роли `ugk_migrator`; `seed-load --purge` в prod отказывает (только dev/test) |
| `restore_test_missing`, `restore_test_overdue` | предупреждение | проверки восстановления нет или она старше 35 дней | `make restore-test` |
| `restore_test_failed` | критично | последняя проверка восстановления неуспешна | журнал в `/var/log/ugekazna`, [backup-restore.md](backup-restore.md) |
| `restore_test_rto` | предупреждение | восстановление дольше 7200 с | анализ производительности хранилища копий |
| `key_rotation_due` | предупреждение | активный ключ данных старше 12 месяцев | ротация ([../security/key-management.md](../security/key-management.md), П3) |
| `tls_cert_expiring` | предупреждение / критично | сертификат истекает через 30 / 7 дней | П8 того же регламента |

Формат `ops-check --json`: объект `{"problems": [{"code", "level", "message"}], "notes": [...]}`
(`level` — `warning` или `critical`; `notes` — сведения без замечаний, например пропущенные правила).
Код возврата 1, если есть хотя бы одно замечание. Команда:
`$P exec -T worker python -m app.cli ops-check --json --tls-cert /run/secrets/tls_cert`
(или `make ops-check STACK=prod` в текстовом виде).

### Ограничения контроля свежести

- `ops-check` (`stale_data`) и индикатор свежести в интерфейсе отражают время последней успешной
  загрузки **любого** источника; свежесть по каждому источнику отдельно не контролируется.
- Сразу после отката сборки (`rollback-build`) `/meta/freshness` по-прежнему показывает «свежие»
  данные — время последней загрузки не меняется; оператор сверяет `active_build_id` в «Сборках
  витрины».

## 5. Оповещения о загрузках

`worker` сам отправляет письма (ТЗ, раздел 9): сбой загрузки (`etl_failed`), нарушение проверок
качества (`etl_quality`), расхождение с контрольными суммами 1С более 0,1 % (`control_totals`),
отсутствие обновления дольше порога (`stale_data`, один раз на эпизод), ошибки строк (`etl_row_errors`).
Письма уходят только при заданных `SMTP_HOST` и `SMTP_TO`; иначе — запись в журнал `worker`.

## 6. Журналы

| Журнал | Где | Хранение |
|---|---|---|
| Контейнеры (JSON) | `$P logs <сервис>` | json-file, 5 × 20 МБ на контейнер |
| Доступ к сайту (Caddy, JSON, без cookie) | `$P logs caddy` | то же |
| Журнал аудита приложения | «Администрирование → Журнал аудита» | не менее 12 месяцев |
| auditd | `/var/log/audit/` | 20 × 50 МБ |
| Проверки восстановления | `/var/log/ugekazna/` | по регламенту организации |

Передача журналов в SIEM организации обязательна: агент на хосте пересылает syslog/journald (теги
`ugekazna-monitor`, `ugekazna-alert`, `ugekazna-restore-test`), `/var/log/audit/` и
`/var/lib/docker/containers/*/*-json.log` ([host-hardening.md](host-hardening.md), раздел 9).

## 7. Производительность СУБД

- Медленные запросы (> 500 мс) — в журнале `db`; планы запросов дольше 2 с — `auto_explain`.
- Топ запросов:
  ```bash
  $P exec -T db psql -U postgres -d ugekazna -c "SELECT calls, round(mean_exec_time) AS ms, left(query, 80) FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10"
  ```

## 8. Перегрузка и пул соединений

API ограничивает число одновременно выполняемых запросов с сессией БД: `DB_POOL_SIZE` (по умолчанию 10 на
процесс uvicorn, т. е. 40 при 4 процессах; пул соединений — вдвое больше). Запрос ждёт свободный слот не
дольше `DB_SLOT_TIMEOUT_SECONDS` (по умолчанию 5 с), затем получает ответ 503 `service_busy` с
`Retry-After: 1`, а в журнале `api` появляется событие `db_slot_timeout` с накопленным счётчиком.
Единичные ответы 503 при пике — штатное поведение; постоянные — признак нехватки ресурсов СУБД или слишком
малого `DB_POOL_SIZE`. Переменные в
`deploy/compose.prod.yml` и `prod.env.example` не вынесены: чтобы изменить значения, добавьте их в
`x-backend-env` и выпустите релиз (запланировано как параметр `prod.env`).
